# Controlled development-to-activation runbook

**Initial state: DORMANT.** This is an outcome/acceptance runbook, not a grant or a verified set of commands. Resolve current target-local/native/SDK commands at their owner before execution. Do not copy obsolete install or deployment snippets from old reports.

## Stage 0: read-only readiness census (U00)

Resolve current refs, WIP/sibling campaign heads, code/blob changes, contract owners, SDK pins, deployed images and exact Staging build. Inspect actual installed optional/Enterprise modules, data counts, registry, native APIs and dynamic consumers. Count existing semantic/graph entities and external identifiers. Read effective authorization without printing secrets. Deliver evidence for F01/F03/F04/F08 and rebind plan digests.

Stop affected scope on missing access or a source conflict. Do not "fix" a live setting to make the inspection succeed. Keep independent read-only investigations moving.

## Stage 1: accept source contracts (U01)

Adopt the minimum ADR amendments, native source mapping, prospect identity, quantity/unit semantics, gap result meanings, external wire contracts and role/caller rules. Resolve F05 before creating the optional bridge/journal. Record exact files and successors; preserve all locked operator decisions. Obtain explicit bounded implementation grants per repository. An approved plan is not activation authorization.

## Stage 2: dormant implementation (U02-U09)

Develop in isolated authorized worktrees and test databases. Ship all business-operation defaults off. No automatic production install, scheduled job, inference call, graph write, mail, partner or PO change. Native brokerage workflow remains the external campaign owner; do not duplicate it. Proposed new files exist only after the whole-plan source frontier is closed.

Use independent lanes only when contracts are frozen and write surfaces disjoint. Review exact code diffs, not just CI. Any newly discovered material effect pauses that unit and updates the plan before edit.

## Stage 3: controlled verification (U10)

Run actual native Odoo 19 Enterprise optional-install/upgrade tests, not only default smoke or Community. Execute the semantic-kernel-specific CRM collision tests. Verify stable identity, provenance, company ACLs, unknown/ranged values, genuine-zero behavior, duplicate/reordered events, rollback and restore. Run EIE/CEG/Gate contract parity with exact SDK images and real graph edges.

Test the full path in a disposable release set. Positive result must be a correct nonempty known match with source and native-record resolution; negative cases must reject the precise wrong candidate. A candidates key or transport 200 is insufficient. All product proofs remain NOT_RUN until actual receipts are produced.

## Stage 4: isolated Staging shadow acceptance (U11)

After the final source build and module upgrades, refresh the exact Staging host/build/configuration. Use authorized controlled source records and safe evidence. Keep production dormant. No buyer email or commercial writes are authorized by this shadow stage.

Prove both industrial-inference directions with grounded positive/defeating examples; verify a confirmed requirement matches an actual current lot; alter/withdraw/reopen the source and verify graph freshness and review behavior. Observe once after deployment and again after a scheduled/worker/retry interval with disable and restart behavior exercised. Capture counts, source revisions, rule versions, graph identities/edges, signed receipts, native-record links, policy scopes and costs. Synthetic fixtures and real-source observations are labeled separately.

Stop on cross-company data, unsupported commercial truth, secret exposure, unapproved spend, duplicate identity, failed source retirement or any unintended outbound action. Preserve evidence and route to exact owner.

## Stage 5: ready-but-disabled gate

Require every applicable proof P01-P34 to be executed and independently reviewed at the exact candidate release. Explicitly disposition non-applicable tests with source-backed rationale, never remove them silently. Require restored-backup proof and current runtime/contract observations. Closed source findings stay closed unless a new contradiction invalidates the affected receipt.

Result is **READY FOR OPERATOR ACTIVATION DECISION**, not ACTIVE. If any required source, contract or runtime proof is unresolved, remain dormant and identify the exact blocker.

## Stage 6: operator activation (U12, separate authorization)

The operator explicitly names target environment, tenant/company scope, immutable release set, permitted operations, budget/limits, observation window and rollback owner. Start with internal read-only intelligence. Controlled confirmed-fact admission/projection and scheduled updates are separately scoped operations. Commercial offer sending is never activated by this kernel.

Before enabling each operation, prove deployed source versions and exact signed caller grants, replay-safe queues, record rules, current listings and tested disable. A global flag, old approval or passed CI cannot substitute. Never broaden to another tenant or source family without fresh authorization.

## Stage 7: observation and recovery

Measure evidence completeness, unknown/conflicting/stale rate, incorrect promotion count, projection freshness, duplicate identities, policy rejections, match correctness, source-to-result traceability, cost and latency. Report scoped usefulness rather than an invented revenue/accuracy guarantee.

Safety acceptance requires zero unauthorized business effects, zero cross-company leakage and zero hypothesis-to-confirmed promotions. Domain inference usefulness/precision thresholds come from the approved evaluation policy, not arbitrary numbers in this pack.

On failure: deny new dispatch, pause pending work, prevent stale graph facts being eligible, retain receipts, reconcile unknown outcomes and restore the pinned proven release/data where required. Do not turn local intelligence back on.

## Activation record requirements

Record operator identity/authorization reference, environment/database/company/tenant, all source and image SHAs, effective SDK versions, exact operations/grants, proof references, source/graph watermarks, migration/restore receipts, budgets, start time, expiry/review time, stop criteria and observed outcome. This pack intentionally includes no filled production activation receipt.
