## Why the plan was stuck

1. **The plan was out of date.** The v2.7.5 ledger is pinned to `677d734f`, 340 commits behind the re-pin head. All seven planned version bumps had already been passed, ADR-129 is taken, and the pack cited invariants v2.2.0 while Staging runs v3.0.0. The pack's own drift rule (`FAIL_CLOSED_RECONCILE_NEW_DIFF`) requires reconciliation before code. v2.8 does that reconciliation (next section).
2. **The pack blocks coding itself.** Two blockers stay open:
   - **S1 (Enterprise check):** the read-only look at a real Enterprise install was never done (the Enterprise source fetch returned 404). The native APIs the plan builds on are unverified: `documents_account`, AI Documents and the dashboard.
   - **Code grant:** never given.

   Coding on unverified APIs is the main source of open-ended debugging.
3. **Nothing could be proven where the code gets written.** A session without the Enterprise source gets CI green with the Odoo tests never run (PR cryptoxdog/IB-Odoo_19#469 merged that way). Export touches 69 existing files across seven modules; without a working runtime test environment every slice would be "looks right, unproven".

## How to build it without contaminating Staging

### Gate 0 — Authorize and re-pin

- Approve the new module (repo rule: ask before adding modules) and give the code grant. **Open: operator.**
- Re-pin the plan to current Staging: recompute versions, the ADR number, the invariants citation and the dependency impact. **Done statically in v2.8** (above and the overlay).

### Gate 1 — Prove the environment works

- Make the Enterprise source reachable where the coding happens: Cursor locally, or a cloud environment with `Quantum-L9/odoo-enterprise`.
- Run `make runtime-bootstrap`, then the S1 read-only check on a copy of the test database. This settles the native-API questions (`documents_account`, AI Documents, dashboard) and the installed versions. The required S1 evidence table is section C09 of `EXPORT_BRS/INTEROP/SOURCE_BOUND_CHANGE_PLAN_v2.7.5.md`.

### Gate 2 — Umbrella branch

- Open `feat/plasticos-export` into Staging and leave it open; it does not merge until the end.

### Merge

Merge the umbrella into Staging only after S6 passes. Then follow the normal Staging → Production promotion.

### Where the risk really sits

Merging the new addon into Staging does not activate it: the module is `auto_install: False`, so it does nothing until someone installs it. The real exposure is the 69 edits to existing modules, which take effect as soon as they merge. Keep those edits additive and test-covered in their own slices.

## Turning the pack into an installable addon

The pack is specification only: 163 files, 120 business rules and acceptance cases, six models and twelve commands, with no Odoo code. To make `plasticos_export` installable:

- **Build the dependencies first.** Export depends on Logistics, Documents and Security Base changes, never the reverse.
- **Scaffold with the `plasticos-new-odoo-module` skill:**
  - **Manifest:** version `19.0.1.0.0`, `application` True, `auto_install` False.
  - **Dependencies:** start from `plasticos_documents_native`. Any non-PlasticOS Odoo module it depends on must be added to `KNOWN_ODOO_ADDONS` in `tests/test_repo_dependency_integrity.py`.
  - **Models:** literal `_name` values.
  - **Security:** ACL and record rules, reusing the existing logistics and operations-manager groups.
  - **Views and reports:** the five views and two QWeb reports the pack specifies.
  - **Mail automation:** `linda_booking_inbound.xml`.
  - **Business rules:** `business_rules/` as above, with its contract test.
  - **README:** with front matter.
  - **Module list:** add it to `odoo_module_order.yaml`.
  - **Tests:** the five test files, mapped to the 120 acceptance cases.
- **Keep Phase 2 out:** FindTEU tracking and the AESDirect export filing stay optional and later.
