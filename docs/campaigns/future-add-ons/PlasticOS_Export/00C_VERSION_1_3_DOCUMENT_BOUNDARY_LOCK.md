# v1.3.0 additive operator lock: Export vs. Documents ownership

**Decision class:** LOCKED_OPERATOR_INTENT; additive to v1.2.0 product planning. **No repository admission, module implementation, or live operation is authorized.**

**Operator direction:** `plasticos_export` is deliberately small: incoming/outgoing document coordination, native QWeb reports, useful Odoo views and only the minimum export-specific fields/links. The ERP, Documents and Logistics do what they already do best. All 16 non-manifest v1.2.0 files are preserved byte-for-byte.

## Locked boundaries

1. **Odoo native Documents + ir.attachment** (when the licensed/installed Documents capability is present) own original files, versions, storage, aliases, internal Inbox, native organization, Requests and file controls. Use approved attachment/Mail fallback when Enterprise Documents is not available; do not create a parallel file store or external sharing portal.
2. **`plasticos_documents`** owns the domain-neutral document compliance vocabulary, typed exact association of evidence to business objects, authoritative business verification/override, source and party attribution, current/expired/superseded evidence logic, and read-only operation-scoped document compliance. Its native bridge projects/delegates to the ONE approved verification writer; native UI must not perform an independent business verification.
3. **`plasticos_export`** owns ONLY export-specific booking/shipment context (Booking No., Steamship Line, POL, POD, Cut Off, ERD and any demonstrated missing linkage), applicability of the document requirements to a particular export shipment/stage/contract, export-specific views, deadlines/exception projections and QWeb report templates. It reads the existing Documents verification result. It must not recreate document storage, verification, rule evaluation, mail sending, BOL/document ledger, freight, financial posting or inventory.
4. **`plasticos_logistics` / Linda via native Odoo Mail** coordinate approved external buyer, supplier, steamship-line/forwarder and carrier communications for operations assigned to that workflow. An export-specific user action may request an authorized document dispatch through this existing owner. Do not create a second sender, mail retry controller, external reminder owner or scheduler.
5. **Odoo Sales, Purchase, Stock, Accounting and reporting infrastructure** remain the authoritative commercial, physical and financial subsystems. Existing `plasticos.transaction` and load models retain their own proven boundaries. Report templates may be defined by `plasticos_export`, but source values and posted facts are read from their existing owners. Stock receipt/shipping and financial posting require native authorized actions.
6. **Exactness and confidentiality:** one source original, many validated typed links if appropriate; no `latest booking`, matching by partner name alone, or cross-company association. Check document applicability, recipient audience and revision at the exact company, booking, transaction/load/container/order, source version and required operation. No unauthorized external native Documents access. No speculative OCR/AI verification or automatic financial effect.
7. **Both product phases inherit the same owners:** Phase 1 supports operator `FOB` = pickup and `FAS` = inland delivery to agreed port/rail; Phase 2 extends the same records for international CFR/CNF/CIF shipment obligations. Industry quotation shorthand remains distinct from an explicitly contracted formal Incoterm. Phase 2 adds export document applicability and reporting, not a second document system.
8. **Minimality test:** for every proposed export field, rule, model, menu, report, job or send action, locate the current owner and concrete missing user action. If a native or existing PlasticOS owner can do it, extend/configure there rather than add it to export. New shared document verification semantics belong to Documents, not Export. Export-specific report layout belongs to Export, not generic Documents.

## Existing seam requiring independent correction, not scope expansion

At source revision `cryptoxdog/IB-Odoo_19@04bd0594a7c9dcad53d9c45fc65276d76817c112`, `plasticos_documents/models/document.py` exposes business `verified`/`verified_by`/`verified_at`, and `plasticos_documents_native/models/document_native.py` also exposes `verified` and an `action_verify()` writing it. The separate Native-First BRS intends ONE authoritative business verifier (`BRS-POS-03-R004`). **Implementation alignment is not proven**. Verify/deconflict against the admitted BRS and current source before relying on document status in Export. This is an existing Documents boundary issue, NOT permission for `plasticos_export` to introduce another verification engine.

## Retained scope and source constraints

The frozen working BRS archive is referenced, NOT imported or modified. Applicable rules include `BRS-POS-01-R001..R003`, `BRS-POS-02-R001,R003,R005..R007,R011`, `BRS-POS-03-R001..R008,R014`, `BRS-POS-09-R003,R005,R006`, and `BRS-POS-10-R003..R005,R015`; verify exact admitted successor in future integration.
