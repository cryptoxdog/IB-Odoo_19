# SM-ODOO-INDEPENDENT-DR-001 | Local Disaster-Recovery Invariants

**Version:** 1.3.0 | **Accepted operator scope:** Odoo.sh native protection + independently controlled AWS backup/recovery.

This is a **project-local, operator-locked policy file**. It does not supersede `IB-Odoo_19/INVARIANTS.md`, the Odoo Documents ownership rules, or L9 canonical law. Changes require an explicit new operator decision; implementation agents cannot soften these invariants to pass a test.

Each rule gives its observable failure condition. If a required witness is unavailable, state `UNKNOWN`, not `PASS`.

| ID | Sharp invariant | Falsifying witness / acceptance boundary |
|---|---|---|
| **DR-001 Native continuity** | Independent recovery must supplement, never disable, replace or silently reconfigure native Odoo.sh production backups. | Native production backup policy changes or backup status becomes inaccessible. |
| **DR-002 Independent control** | Copies required for emergency restore, decryption keys, the recovery code/artifacts, and restore credentials must remain under Scrap Management control, usable without Odoo.sh connectivity or approval. | A recovery test requires Odoo.sh to provide a missing byte, key, code dependency or credential. |
| **DR-003 Complete point-in-time state** | Each admitted checkpoint represents one internally consistent database state and its exact referenced filestore versions; retain exact code/dependency/configuration coordinates separately. | New/updated/deleted record or attachment references cannot be reconstructed at the checkpoint time. |
| **DR-004 Transactional semantics** | Record-level export or `write_date` alone is NEVER a disaster-recovery backup; a changed parent without dependent rows, deletion/tombstone, sequences, or other durable database state is incomplete. | Restored PO/SO/transaction relations or deletions disagree with source checkpoint. |
| **DR-005 One original per content identity** | Reuse previously protected bytes when content hashes match; don't re-upload unchanged content just to create another snapshot. Preserve separately each exact recovery point and its manifest. | Identical immutable data repeatedly stored without justified platform limitation, or dedup changes file identity/contents. |
| **DR-006 Immutable dependency closure** | For every protected snapshot, all required chunks/files, database archive, manifests, code metadata and decryption keys must remain available for at least that snapshot's protected lifetime. Never prune or cold-tier a live dependency. | Deleting/archiving an older object breaks any newer checkpoint restore. |
| **DR-007 Vault hard boundary** | Production Odoo credentials and the backup writer cannot delete backup versions, bypass or shorten retention, deactivate independent alerts, administer encryption keys, or grant themselves vault-admin powers. | A backup-runner credential can alter or destroy a protected checkpoint or key. |
| **DR-008 No shared failure domain** | Vault IAM/bucket/KMS administration is isolated from Odoo.sh and ordinary application credentials. Protect against compromised Odoo accounts and compromised production runners. | Odoo admin/session or runner principal can administer the independent vault. |
| **DR-009 Recovery-before-readiness** | `PROVEN` requires a successful independent full restoration of the selected source point into Odoo 19 Enterprise with checks for records, attachments, deletion semantics, ACLs and disabled outbound integrations. | Only object upload/hash, `pg_restore --list`, test-fixture restore, or vendor-side restore was exercised. |
| **DR-010 Schedule as requested** | Independent jobs START Mon-Fri at 11:00, 13:00, 15:00, 17:00 `America/New_York`, with daylight-saving handling and a no-overlap lock. Native Odoo daily backups continue outside that schedule. | A weekend/night independent trigger starts, a job overlaps, or DST triggers twice. Jobs may complete after 17:00. |
| **DR-011 Freshness truthful** | Track immutable `source_checkpoint_at`, `source_backup_completed_at`, `vault_verified_at`, `restore_verified_at`; calculate age from the source checkpoint, not job start or file upload time. | An 11:00 re-download of an earlier native backup is reported as an 11:00 recovery point. |
| **DR-012 Measured RPO** | <=2 operating hours is a target, not a guarantee. Admit the target only when actual source snapshots, transfer latency, missed-job behavior and monitored results support it. | Dashboard reports green from triggers alone, a failed/stale backup, or a source snapshot older than the claimed RPO. |
| **DR-013 Non-destructive collection** | Backups obtain data read-only through authorized Odoo.sh interfaces. No production Odoo modules/fields/cron, database settings, schema, mail, posting or stock changes to support acquisition without separate authorization. | Any backup step writes to operational Odoo records or installs a persistent backup daemon on Odoo.sh. |
| **DR-014 Evidence before promotion** | Failed/partial/corrupt/stale copies never become the latest recoverable checkpoint. Persist per-run evidence, hashes, file counts, checks, gap reason and alerts. | A partial upload is shown as successful or silently advances last-good. |
| **DR-015 Operational secrecy** | Never store secrets, live business exports, customer attachments, private keys or unredacted production manifests in Git, logs, chat or public buckets. | Sensitive bytes appear in a commit, public S3 ACL, telemetry or deployment log. |
| **DR-016 Cold archival is recoverable** | After >=365 days, archive only selected self-contained checkpoints or sets with proven full dependency closure; keep all dependencies of recent points online at the required restore speed. Live business file age does not cause deletion/tiering in Odoo. | A recent restore blocks on Glacier or a monthly archive is missing its historical chunk. |
| **DR-017 Budget and access bounded** | Before cloud mutation, bind exact AWS account/region/role, least privilege, owner/tags, estimated recurring cost, retention liability and a cost alarm. Do not modify unrelated AWS resources. | Unknown account, uncontrolled spend, root credentials or changes outside declared resource scope. |
| **DR-018 Full blast radius before code** | Before implementation, account for all affected repository files, external cloud resources, Odoo.sh access, dependencies, schedules, IAM/KMS, security, cost, restore/license requirements and failure/rollback paths. No code until the dependency/effect matrix is reconciled. | A hidden required permission, side effect, owner or file appears only after writing the implementation without a documented plan. |
| **DR-019 Isolated test and cutover** | Restore tests may use synthetic data or protected real backups only inside isolated nonproduction environments with outbound mail/payment/shipping/webhooks disabled. Production restore, DNS switch or subscription reassignment require a separate incident/operator decision. | Test restore emits customer mail or modifies live Odoo/DNS/subscription. |
| **DR-020 No fake proof** | Source presence, ERP corpus success, a ZIP, passing unit tests or an untested Terraform plan cannot substitute for observed Odoo.sh source capture + independent AWS restore. | A delivery claims `COMPLETE` without exact dated restore evidence. |
| **DR-021 Infisical is secret SSOT** | Every newly generated persistent DR workload credential, private key, password and bearer secret (excluding 1Password account login and AWS KMS nonexportable material) is entered into the authorized Infisical project/environment/folder before use, with owner, scope, rotation and tested retrieval. Prefer zero static AWS keys. | A newly generated secret exists only in a local `.env`, Git, Terraform state or worker; secret is untracked in Infisical. |
| **DR-022 Configuration is reproducible** | Safe non-secret configuration, schedule, AWS/IAM/KMS/S3 definitions, consumer pointers and native-backup procedures are documented in version-controlled source. Sensitive runtime/deployment state is encrypted separately; no secret values or customer data are committed. | AWS is hand-clicked with no reproducible source, or a secret/runtime state is committed. |
| **DR-023 Infisical failure cannot block DR** | A tested, independently controlled sealed break-glass recovery path preserves minimum AWS vault-read/KMS-decrypt/Odoo restore access when Infisical, Cursor, Odoo.sh and the normal runner are unavailable. | Emergency S3 restoration needs a token retrievable only from the unavailable Infisical instance. |
| **DR-024 Native backup contract isolated** | Provider-native backup verification, a supported native manual checkpoint and a safe native restore belong only to Contract 01. AWS vault/identity, full restore, efficient scheduling and recovery custody belong to Contracts 02-05; Contract 06 integrates evidence without taking over owners. Each boundary has a separate receipt. | AWS executor silently alters native production settings or native executor creates cloud infrastructure. |
| **DR-025 Native source is real Production** | A native backup readiness claim requires observed Odoo.sh Production project/build/database identity and actual completed full database+filestore backup with source time and revision, not a staging/dev backup or download-time guess. | An agent reports protected Production while it only inspected staging or an empty backup listing. |
| **DR-026 Native controls are provider-bound** | Verify and exercise only genuine Odoo.sh native backup controls. Provider-managed cadence/retention is recorded as verified, never falsely marked configured. One manual backup may be requested under official UI/access limits; no invented API or script bypass. | Claims hourly native scheduling via an undocumented endpoint, or attempts hidden UI scraping. |
| **DR-027 Native restore is non-destructive** | Native restoration proof occurs only in an isolated approved nonproduction target with external side effects disabled; never restore/import over live Production. | A backup test overwrites production records or delivers external emails, payments or shipping actions. |
| **DR-028 No secret/infra ownership drift** | For every secret and configuration entry record unique owner, storage, consumer, privilege, rotation/recovery and test; do not create a competing secrets authority or duplicate provider-managed settings locally. | A recovery secret has no owner, or a backup writer can change Infisical DR admin secrets or KMS administration. |
| **DR-029 IaC state is independently protected** | Deployed infrastructure state and outputs, when used, are encrypted, access-scoped, versioned and recoverable outside Git; secret values must not be persisted in the state. | `.tfstate`, credentials or sensitive deployment inventory appears in repo/CI artifacts, or a re-provisioning test cannot resolve state. |
| **DR-030 Contract-specific proof and release** | Native verification, AWS protected vault, off-Odoo restore, incremental proof, 1Password custody and two-hour operational proof are separate gates; a succeeding phase cannot inherit a missing predecessor witness. Code changes use bounded, verified publisher, no merge/cutover. | A native backup created is described as independent AWS ransomware recovery, or AWS vault exists without restoring production. |

| **DR-031 Operator custody is real** | The emergency recovery package is *actually created and verified* in the restricted company-controlled 1Password vault, with recorded document/item IDs, not merely mentioned in a runbook. Operator-specific access must be tested. | No live `op document` result; item cannot be found/retrieved from authorized vault or was placed in a shared/general vault. |
| **DR-032 No circular password-manager bootstrap** | 1Password sign-in recovery information and required MFA recovery method must exist under independent operator custody OUTSIDE 1Password. 1Password content may not be its own sole unlock method. | Operator loses all devices and cannot sign in without an item stored only in locked 1Password. |
| **DR-033 Infisical and 1Password have different roles** | Infisical remains runtime SSOT for all new persistent secrets; 1Password holds only the minimal intentional emergency escrow and recovery document, with owner/revision/rotation mappings to Infisical. | A routine worker reads passwords from 1Password, a new secret is missing from Infisical, or copied escrow is stale with no rotation rule. |
| **DR-034 No accidental local pack** | With verified 1Password custody, no long-lived recovery pack is placed on Mac, Dropbox, iCloud, Git, shell history or worker storage. If operator explicitly approves a Mac fallback, it must be encrypted, private, off-sync, access-checked and its custody recorded. | A secret ZIP remains in ~/Dropbox, ~/Library/CloudStorage, iCloud-synced Documents or an unencrypted desktop folder. |
| **DR-035 Artifact is human-executable** | The emergency package contains tested operator instructions, last-good checkpoint selection, AWS/KMS/IAM recovery paths, IaC/state and code provenance, vendor rights, contact/escalation path, safe restoration and integrity/verification steps. | Recovery requires Cursor's memory, current repo availability or undocumented commands/identities. |
| **DR-036 Custody is verified by retrieval** | A separate operator-authorized session must re-download the exact protected 1Password document, verify SHA-256 and open/rehearse its steps without relying on the creating CLI session. | 1Password upload says success but download fails, bytes differ, or only the agent can access the vault. |
| **DR-037 Secure temporary handling** | Any transient generation uses an isolated, nonsynced, owner-only encrypted or memory-backed workspace and authenticated CLI, with logs/history/process args/OS metadata protections. Completion confirms cleanup and records remaining forensic limitations; never claim guaranteed SSD deletion. | Secrets are echoed, written to persistent synced directories, included in CI/state or left in world-readable temp paths. |
| **DR-038 Break glass without normal services** | Independent restore is rehearsed without Odoo.sh, Infisical, normal backup worker, Cursor session and original Mac; authenticated 1Password access plus AWS/KMS control must still suffice. | A restore step needs an Odoo/Infisical token, a deployed worker secret or a file remaining only on the Mac. |
| **DR-039 Contract closure is atomic** | Every slice finishes its own code/config/secrets/tests/alerts/cost/cleanup/handoff and publishes an evidence-bound receipt; unresolved in-scope items prohibit PASS. Genuine externally owned blocker is named and campaign remains NOT_DONE. | A contract says DONE with a TODO, missing test, missing credential owner or silent postponed work. |
| **DR-040 Campaign DONE is conjunctive** | Campaign DONE requires every mandatory slice PASS, observed native restore, independent AWS restore, valid fresh and incremental scheduled checkpoints, 1Password custody/retrieval and adversarial rehearsal. No partial milestone or PR may substitute. | Vault exists but no scheduled fresh point, or four jobs run but no real restore, yet DONE is declared. |
| **DR-041 Changes invalidate affected proof** | Any change in Odoo build/source, backup method, IAM/KMS, 1Password escrow, retention policy, software revisions or restore implementation invalidates specifically dependent proofs until rerun. | Old PASS receipts are reused after materially changing the source or security configuration without compatibility proof. |
| **DR-042 Dependency and rotation continuity** | Every access route and secret has a named owner, expiry/rotation process, Infisical secret ID reference, emergency escrow refresh procedure and live access test, including disabled credential scenarios. | Credentials rotate while the emergency package still references revoked values. |
| **DR-043 Strict source scheduling claims** | A 2-hour schedule is not a 2-hour RPO guarantee. Source capture and upload delays, 09:00-11:00 gap, Friday-to-Monday window, and overnight mutations must be measured or explicitly excluded, and failures trigger alerts without fake success. | A clock trigger alone proves SLA, the 11 AM point is not yet retrievable, or an overnight change is silently claimed covered by the independent schedule. |
| **DR-044 Cold tier never compromises recovery** | Only source-point-consistent, standalone historical archives older than 365 days may transition cold after trial restore and complete dependency/crypto closure; recent points stay hot. | A recent restore needs a Glacier-only object or the archive depends on a deleted dedup chunk. |
| **DR-045 Recovery pack is maintained** | A policy/key/role/license/backup-method/version change must trigger a refreshed 1Password recovery document, restored re-check and removal/retirement of obsolete instructions; quarterly review is mandatory. | Live AWS identities and documentation diverge or old recovery secrets are trusted indefinitely. |
| **DR-046 Provider access is an actual gate** | No unverified private Odoo API or unauthorized SSH/SQL extraction may satisfy the source checkpoint schedule. If source access cannot produce fresh consistent points, exact provider/plan blocker remains open and campaign is not DONE, while safe partial protection proceeds. | Re-downloaded nightly backups presented as four fresh captures, or an unsupported Odoo method silently deployed. |

| **DR-047 Independent emergency authentication** | Emergency 1Password access and AWS IAM/KMS recovery must not depend on the same compromised Odoo/Infisical/worker identity or on a single unavailable IdP, with required MFA under separate custody. Prove an alternate lawful auth path. | Both 1Password and AWS recovery access require the disabled SSO/IdP, or possession of the 1Password document alone grants unscoped AWS administrator powers. |
| **DR-048 Preserve year-one and cold retention** | Selected archival checkpoints must remain accessible through their first 365 days and beyond for explicitly retained cold archive; a 90-day Object Lock minimum is not a 365-day retention policy. Never silently delete a checkpoint at the end of WORM retention. | All selected monthly/yearly archive checkpoints expire before reaching cold eligibility, or cleanup automatically deletes the last independent historic checkpoint. |

| **DR-049 Independent checkpoint admission** | The routine backup writer may submit candidate bytes only; a separately authorized verifier must validate source-time, integrity, complete dependency closure and immutable retention before it alone publishes an admitted manifest and advances last-known-good. The writer cannot promote its own backup or alter the admission index. | A compromised writer changes `last-good` or creates a forged admitted manifest without independent verification, or a corrupt candidate becomes the selected recovery point. |

## Interpretation limits

- A **native Odoo.sh automatic backup**, an **independent Odoo.sh backup copy in S3**, a **fresh two-hour checkpoint**, and a **proven outside-Odoo restore** are four separate verifiable states.
- AWS S3 Object Lock Compliance mode does not prevent losing access to KMS keys; key availability is part of DR-002 and DR-006.
- Immutable chunks may be reused but must have retention extended or otherwise protected against deletion until ALL dependent snapshots' protection periods end.
- Odoo.sh's platform API for automated manual backup creation has not been proven; do not invent one or substitute business-row synchronization.
