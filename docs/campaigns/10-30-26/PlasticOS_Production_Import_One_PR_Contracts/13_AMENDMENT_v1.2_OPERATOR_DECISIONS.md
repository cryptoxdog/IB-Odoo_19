## Design bindings that implement D2 and D3

| Surface | Binding |
|---|---|
| Production detection | Unchanged: `ODOO_STAGE=production` or a database name containing `prod`/`production`. Without a verified permit, both still refuse. A permit lifts the refusal only when `ODOO_STAGE=production` **and** the observed database matches the permit, so a production-named scratch database cannot unlock it by toggling `ODOO_STAGE` or `ERP_TARGET_DB`. |
| Permit fields | `permit_id`, `phase` (`erp_partners`, `erp_commercial`, `crm_history`), `database_name`, `database_uuid` (`ir.config_parameter` `database.uuid`), `odoo_stage`, `release_sha` (clean `git` HEAD of the addon checkout), `source_fingerprint` (ERP: SHA-256 of the projected tables the phase reads; CRM: census SHA-256), `expires_at` (UTC, at most 24 h ahead), `approved_by`. |
| Permit transport | `ERP_PRODUCTION_PERMIT` / `VANILLASOFT_PRODUCTION_PERMIT`: a file path on the host. Never committed and never stored in Odoo settings. No environment-only allow switch exists. |
| Consumption record | ERP: `plasticos_partner_import.production_permit.<permit_id>`. CRM: `plasticos_crm_sync.production_permit.<permit_id>`. The value is redacted JSON (bindings, consumed time, no secret). |
| Phase order | `erp_partners` requires the empty-business-partner guard (`ERP_REQUIRE_EMPTY=0` refused), and writes the witness `plasticos_partner_import.production_phase1_witness` in the partner commit. `erp_commercial` requires that witness for the same database UUID and partner-table fingerprint. If the witness is not data-complete, the permit must carry `accept_phase1_exceptions_digest` equal to the witness exceptions digest. `crm_history` requires the commercial completion record `plasticos_partner_import.production_phase2_witness`. |
| Production refusals | `ERP_LIMIT`, `ERP_PAYLOAD_ROOT`, a non-SQL source, single `ERP_LAYER` runs, and dry runs that do not roll back. |
| Source drift | The importer computes the fingerprint of the payload it actually loaded, right after loading and before any stage writes, and refuses on mismatch. Resume is a full idempotent re-run under a new permit bound to the same fingerprint. |
| Data acceptance | `exit 0` is script completion only. Each receipt carries `data_complete` (true only for `success` with no failures). It also carries `accounting_state: draft_unposted` and `accounting_acceptance: BLOCKED_ARCHITECTURE` until an approved source-status mapping exists. |
| CRM checkpoint | The checkpoint is a JSONL ledger at an operator path, headed by the census digest and database UUID. Authority for "imported" is the durable `plasticos.crm.external.ref` row. A checkpoint row is never trusted alone. Non-imported rows are retried on resume; deterministic duplicate skips are not. |
| CRM fencing | The runner holds the connection's session advisory lock, the same key the cron and manual sync use. It refuses when the lock is held or when the VanillaSoft cron is active. |
| CRM omitted duplicates | Staging carries no `OMITTED_DUPLICATE_VS_IDS` (it exists only on unmerged branches). The four IDs from the v2 contract (`1045036935`, `1179868294`, `584402429`, `585278462`) are a cohort constant in `historical_cohort.py`. They are absent from the packaged crosswalk, and the runner records them as `duplicate_skipped` without a fetch, because the per-ID upsert would turn an unbound ID into a new lead. |
| CRM bounds and side effects | `VANILLASOFT_HISTORY_MAX_IDS` bounds one session and `VANILLASOFT_HISTORY_FAILURE_BUDGET` (default 25 consecutive failures) stops a run. The client keeps its existing bounded 429/5xx backoff. A rejected credential stops with exit 2. Lead writes run with `tracking_disable`, `mail_notrack` and `mail_auto_subscribe_no_notify`, so no assignment or tracking mail is queued. History mode needs the ERP contacts stamp on every target. `make import-vanillasoft` without a census keeps its existing semantics. |
| Cross-module | `plasticos_crm_sync` does not import `plasticos_partner_import`. The CRM permit verifier is local to `plasticos_crm_sync`, and a parity test holds both verifiers to the same decision table. |
